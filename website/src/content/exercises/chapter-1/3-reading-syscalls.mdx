在前面的练习里，我们挂到了调度器（`sched_process_exec`）上。这个事件是在内核*已经*加载完二进制、并填好内部结构*之后*才触发的。

那么在*那之前*发生了什么？当 `bash` 这样的程序想运行 `ls` 时，它会通过 `execve` 系统调用向内核发出请求。

系统调用与我们目前用过的具体 tracepoint 不同。它们使用的是对所有系统调用都通用的 `entry` 和 `exit` 事件。

## 通用的系统调用结构

因为系统调用有*几百个*（`open`、`write`、`execve`……），每个都有自己的参数集合，所以内核为它们使用了一个通用的 tracepoint 结构。

在 entry 事件中，我们收到的上下文类型是 `struct trace_event_raw_sys_enter`：

```c
struct trace_event_raw_sys_enter {
    long int id;               /* Syscall number */
    long unsigned int args[6]; /* Arguments */
    /* ... */
};
```

我们拿不到 `name` 或 `pid` 这类方便好用的字段 —— 得到的只有系统调用号（`id`）和一个整数数组 `args[6]`，也就是系统调用的参数。

为什么是 6？因为这是系统调用允许接受的最大参数个数。

我们*也*拿不到任何类型信息！所有参数都是 `long unsigned int`（`u64`），把它们正确地解释为我们想要的东西（指针、结构体、有符号数，甚至 `u64`！）是我们自己的责任。

要知道每个参数的类型和含义，你可以查阅[手册页](https://man7.org/linux/man-pages/man2/execve.2.html)，里面给出了函数签名：

```c
int execve(const char *filename, char *const argv[], char *const envp[]);
```

由于 `filename` 是第一个参数，它位于 `ctx->args[0]`。`args` 数组把它存成 `unsigned long`，所以我们需要把它转换成 `const char *`。

### 关于地址空间

`ctx->args[0]` 指向调用进程（例如 `bash`）拥有的内存，那是**用户空间**内存。

出于安全考虑，内核对用户内存和内核内存执行严格隔离。这意味着我们不能用之前用过的那些内核空间辅助函数（比如 `bpf_probe_read_kernel_str`）来读这份数据。我们必须改用 [bpf_probe_read_user_str(dst, size, src)](https://docs.ebpf.io/linux/helper-function/bpf_probe_read_user_str/)。

## 你的任务

1. 从 `ctx->args[0]` 构造出 filename 指针。
2. 把字符串从**用户空间**读进一个本地缓冲区。
