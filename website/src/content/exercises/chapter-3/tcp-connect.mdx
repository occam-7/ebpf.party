
我们已经用 tracepoint 挂载到系统调用上。现在来认识 **kprobes** —— 直接附加到内核内部函数上。

## kprobe 与 tracepoint 的对比

**Tracepoints** 是内核特定事件处（系统调用进入/退出、调度等）稳定的、有文档记录的挂载点。它们提供结构化的上下文：
```c
SEC("tracepoint/syscalls/sys_enter_connect")
int trace(struct trace_event_raw_sys_enter *ctx) {
    u32 fd = ctx->args[0];  // Predefined fields
}
```

**Kprobes** 则按函数名附加到任意内核函数上。

这种机制更灵活，但 kprobe 不属于内核的稳定 API，因此可能在不同内核版本之间发生变化。除此之外，它们也不提供预先定义好的「上下文」，我们需要从内核源码中确定参数的类型和顺序。

## 为什么要用 kprobe？

tracepoint 只暴露特定的事件。kprobe 则让我们能更深入地挂到内核内部。例如，对于非阻塞 socket，`connect()` 系统调用会立即返回，但 TCP 握手真正完成时调用的是 `tcp_finish_connect()`。

## 访问函数参数

kprobe 收到的是 `struct pt_regs *ctx` —— 原始的 CPU 寄存器。用宏来提取参数：

```c
PT_REGS_PARM1(ctx)  // First parameter
PT_REGS_PARM2(ctx)  // Second parameter
PT_REGS_PARM3(ctx)  // Third parameter
// up to 8
```

我们可以找到 `tcp_finish_connect` 的签名，它位于 `net/ipv4/tcp_input.c`，即
```c
void tcp_finish_connect(struct sock *sk, struct sk_buff *skb);
```

因此，要拿到 `struct sock*`，需要把**第一个**参数做强制转换：
```c
struct sock *sk = (struct sock *)PT_REGS_PARM1(ctx);
```

## 挑战

某个程序会连接到一台远程服务器。`connect()` 系统调用返回 `-EINPROGRESS`（非阻塞），但连接最终成功建立。

### socket 的属性

你可以用 `bpf_probe_read_kernel` 读取 socket 的属性。这里是相关的字段：

```c
struct sock {
    struct sock_common __sk_common;  // Common socket info
    // ...
};

struct sock_common {
    u16 skc_dport;   // Destination port
    u32 skc_daddr;   // Destination IPv4 address
    // ...
};
```

注意端口是大端序，所以需要用 `bpf_ntohs` 来转换。
